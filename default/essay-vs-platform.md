# 数据工程工作论文系列与 qtcloud-data 实物对照

## 背景

两条线在同一领域并行演化：

- 工作论文系列（`docs/essay`，quanttide-essay-of-data-engineering v0.1.1）：五篇论文提出四层形式化工程方法论——数据需求、数据意图、数据规格、数据实现。
- 实物（`apps/qtcloud-data`）：qtcloud-data CLI v0.3.0（crates.io `qtcloud-data-cli`，含 Linux / Windows 二进制）+ Go Provider + Flutter Studio，已发布并有交付记录。

两边约定不互相引用，各自独立演化。本报告承担对照职能，记录双方的张力所在。

## 对照：四层框架的命令化

CLI 的命令序列与四层框架的对应关系：

| 方法论层级 | CLI 命令 | 实物形态 |
|:--|:--|:--|
| 数据需求（价值合同） | `clarify` | 从客户聊天记录生成 DRD 数据需求文档 |
| 数据规格（约束合同） | `design contract` / `design blueprint` | 生成契约与蓝图（YAML + MD + HTML） |
| 规格验收 | `spec` / `review` | 规格 envelope 固化与完整性审计 |
| 数据实现（工程合同） | `implement` | 从蓝图 YAML 生成 Python / R / Stata / Matlab 代码 |
| 执行 | Provider `POST /blueprints/{name}/runs` | Go 后端按蓝图 YAML 的状态机执行 pipeline |

examples 中的规格书范例是直接证据：Part A 契约列输入输出与质量承诺（去重率 100%、Bot 识别准确率下限），Part B 蓝图画处理流程。论文主张「契约约束数据形状、蓝图约束过程」，`design` 生成 YAML、Provider 顺 YAML 执行，链路已经跑通。

## 核心张力：实物在反驳论文的中心主张

论文的中心主张是「人的不可替代性在设计：蓝图必须由人显性写下」。但实物的命令序列里，`clarify from-chat` 生成需求文档，`design` 生成契约与蓝图，`implement` 生成代码——论文说必须留在人手里的设计层，恰恰是产品自动化得最彻底的一层。人在链路里退到了「聊天」和「验收」。

这不是实现偏离理论，而是实现在回答一个论文没有正面回答的问题：如果设计也能生成，人站在哪里？论文的隐含答案是「人写蓝图」，实物的实际答案是「人审批蓝图」。两者不一样，实物更接近事实——`review` 审计完整性与质量承诺验收，才是真正未被生成替代的环节。

## 三个投影

其一，形式化与可执行。intent 篇主张用范畴论描述蓝图，什么不变、什么在变在图上可检查；实物用 YAML + CUE 状态机，可执行、可版本化，但一致性靠约定校验而非数学保证。论文的「形式化验证」在实物里只兑现到「结构化描述 + 校验命令」。

其二，契约绑数据与登记簿绑管道。contract 篇论证「契约绑定数据本身，不绑定管道」；而 `registry.json` 的状态机是 received → processing → processed → delivered 的交付管道生命周期。理论走到下一步，产品的数据模型停在上一步。

其三，通用方法论与交付生意。论文的图景是智能体时代的数据云：本地 catalog、任意方向、人机共图；实物的重心是数据交付：`clarify from-chat` 面向客户、`transfer` 跨平台搬运、`final_delivery` 交付物、质量承诺面向客户。实物被业务塑形，理论被趋势塑形。若以实物为参考实现，方法论目前实际验证过的版本比论文宣称的窄——是「数据交付的形式化」，不是「数据工程的形式化」。

## 判断：张力命名并分层，不消除

第一，生成可以吃掉内容，不能吃掉验收。需求文档、蓝图、代码由谁写不重要；质量承诺、契约校验、可证伪命题这些验收权不进生成路径。论文的角色主张应改写为「人拥有验收权，而非设计执笔权」——这是实物已经证明的一致。

第二，理论给实现状态打标。范畴论明确标注「方向，未实现」；YAML + CUE 明确标注「现行形式语言」。双轨演化本身没有问题，问题在于不承认对方是自己的另一个版本。

第三，catalog 是张力落到代码的战场。「绑定数据不绑定管道」若成立，registry.json 需从管道生命周期改造为数据生命周期。catalog 论文的「本地版 Data Catalog」提案（索引任意异构来源）正是 registry.json 现状的推广方向：从「我交付过什么」扩展到「本地有什么可以处理」。

两边不互相引用，各自独立演化；对照与张力由本报告及后续报告承担。
